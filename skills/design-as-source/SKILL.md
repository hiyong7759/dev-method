# 설계 = 소스 — 주석과 커밋

목적: 설계문서 없이 **존재 이유 주석과 코드만 보고** 다음 에이전트가 "적정하게 구현됐다/덜 됐다"를 판정할 수 있게 하는 것. 히스토리는 커밋에서 찾게 해 주석이 시간이 지나도 커지지 않게 하는 것.

## 존재 이유 주석

- 파일 헤더 = 이 파일이 왜 있나 (몇 줄). 컴포넌트(함수·클래스·설정 묶음) 바로 위 = 그것이 왜 있나
- 새 컴포넌트를 만들면 존재 이유 주석을 함께 쓴다. 이유가 달라졌을 때만 고친다
- 동작 설명을 주석으로 반복하지 않는다(어떻게는 코드가 말한다). 이유와 코드가 어긋나면 둘 중 하나를 고친다
- 히스토리(예전엔 A였다가 B로)와 기각은 주석에 쓰지 않는다. 커밋에 있다
- 출처: 외부 근거(법령, 표준, 논문, 측정 데이터)는 이름을 적는다. 사용자 결정은 사용자가 그 내용을 직접 말한 것에만 `(사용자 결정)`을 단다
- 숫자 상수(문턱, 시간, 비율)에는 근거를 적는다. 모르면 지어내지 말고 "근거 없음"이라 적는다
- 측정값에는 날짜를 붙인다(`2026-10-14 측정`). 다시 재지 못한 옛 값은 그렇다고 표시한다
- 주석의 주장은 코드가 실제로 그렇게 하는지 확인한 것만 쓴다. 파일 사이 연결 주장("X가 이 값을 바꾼다", "아무도 안 쓴다")은 쓰기 전에 grep으로 확인한다
- 다른 사례(논문·공개 코드)를 따른다고 쓰려면 그 사례의 실제 코드와 항목별로 대조한 뒤에 쓴다. 다른 점은 이유와 함께 적는다
- 주석을 달 수 없는 JSON은 그 묶음의 `about` 문구가 존재 이유 주석이다
- 주석이 20줄 안팎을 넘으면 파일이 너무 많은 일을 한다는 신호로 보고 나누기를 제안한다

## 커밋 메시지

성공이든 실패든 모든 작업을 커밋으로 남긴다. 결정·기각은 여기에만 남으므로 나중에 찾을 수 있게 표시를 붙인다.

```
<종류>: <무엇을 바꿨나 한 줄>

<왜 바꿨나, 1~3줄>
결정: <앞으로도 지킬 선택> — <이유>
기각: <해 보고 버린 길> — <이유>
검증: <완료 기준과 결과 숫자, 스크린샷 경로>
```

- 종류: `feat`(새 기능) `fix`(고침) `tune`(값 조정·학습) `chore`(정리) `check`(코드 변경 없는 검사 결과)
- `결정:`/`기각:` 줄은 해당할 때만, 한 줄에 하나, 줄 맨 앞에
- 실패한 코드 변경은 커밋 뒤 `git revert`로 되돌린다(둘 다 기록). 실패 커밋 제목에 `실패:`를 붙이고 `검증:` 줄에 무엇이 왜 안 됐는지 숫자로
- 코드 변경 없는 시도·검사 결과는 `git commit --allow-empty`로
- 파일의 결정·기각 찾기: `git log --format='%h %ad %s%n%b' --date=short -- <파일> | grep -E '^[0-9a-f]{7}|^(결정|기각):'`
