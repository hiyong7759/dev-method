# 승인 (요청 단위)

승인은 화면마다 하지 않고 **요청 단위**로, **사용자만** 한다. 요청 하나는 설계 → 구현 → 테스트 → 완료를 거치고, 설계와 테스트에서 사용자 승인이 필요하다. 모든 변경은 요청 번호가 있어야 한다.

## 에이전트가 하는 일 (명령은 `node <스킬 폴더>/spec.mjs request <명령> --src <소스 폴더> …`)

1. **요청을 받으면** `request add --title "…" --origin "사용자가 한 말" --screens … --infos … --scenarios …`로 등록한다. 범위는 사용 시나리오 기준이다(`--scenarios`), 이번 요청이 바꾸는 단계는 `--steps "시나리오#단계,…"`, 바꾸지 않고 영향만 볼 시나리오는 `--impact`. 맡은 세션 이름은 `request agent --id N --name …`
   - **테스트 범위는 이번 변경과 관계 있는 단계만 고른다**: 사용자가 테스트에서 누르고 확인하는 항목은 범위에 연결한 시나리오 단계가 그대로 된다. 시나리오를 통째로 연결하면 이번 변경과 상관없는 단계가 확인 항목으로 올라와 테스트가 의미 없어진다. 그래서 시나리오만 적지 말고 `--steps "시나리오#단계,…"`로 이번에 바뀐 동작을 확인하는 단계만 연결한다. 바뀐 동작에 맞는 단계가 소스에 없으면 먼저 `@does`로 그 동작(무엇을 누르면 무엇이 보이는지)을 단계로 올린 뒤 연결한다. 바뀌지 않지만 깨질 수 있는 곳은 `--impact`로 "영향 확인만"으로 둔다. 확인 기준은 이번 변경이 실제로 어떻게 보여야 하는지를 적는다("화면이 열린다" 같은 어느 변경에나 맞는 말은 쓰지 않는다). 사용자 말: "테스트 내용도 실제 필요한 테스트 내용이 아닌게 너무 많아서 의미가 없다"
2. **설계**: 정보나 화면이 바뀌면 설계를 올린다. `request design --id N --file 설계.json`. 파일 모양은 `understanding`(이렇게 이해했다: 짧은 한 줄 요약), `points`(영역별 항목: area 영역, title 바뀌는 것, text 설명 — 화면이 영역·바뀌는 것·설명 표로 보인다. 글 기호는 쓰지 않는다. 설계 없음이어도 항목이 둘 이상이면 `points`로 적는다), `approach`(이렇게 처리하겠다: 정보·화면 변경이 없는 "설계 없음" 요청에서만 쓰고 보인다. 항목이 하나뿐인 짧은 설명에만 쓴다), `changes`(정보 변경: info, kind add|remove|change|link, field, note — 화면에는 정보 하나에 한 줄 요약으로 보이고 자세한 것은 "정보 변경 겹쳐 보기"), `screens`(화면 디자인: screen, after 시안 그림 파일, note, counts, highlights 현행과 달라진 곳의 위치·이름, isNew), `data`(이미 있는 데이터·되돌리기·실제 데이터). 정보도 화면도 안 바뀌면 `request design --id N --none true`("설계 없음")
   - **현행과 시안**: 비교하는 "현행"은 지금 운영 중인 화면을 손대지 않고 그대로 찍은 것이어야 한다. 행을 숨기거나 지우거나 글자를 바꿔 찍지 않고, 지난 시안을 현행으로 쓰지 않는다. 고친 모습은 `after`(시안) 그림에만 얹는다. 현행은 `request shot --id N --screen 화면이름 --url 운영 화면 주소 [--selector css]`로 찍는다(ego-browser로 열어 찍고, 도구가 찍은 시각과 주소를 남기고, 설계를 올릴 때 이 그림이 현행으로 붙는다). 파일로 직접 올린 `before`는 "손으로 올림(현행이 아닐 수 있음)" 경고가 붙는다
   - **시안(after)은 현행과 같은 틀 안에서 그린다**: 시안 그림은 현행 그림과 같은 너비·같은 틀(상단 헤더·내비·프로젝트 이름·옆 패널·같은 테마와 글자 크기)에 바뀐 부분만 다르게 보여야 한다. 바뀐 영역만 따로 그린 맨 화면(앱 틀 없음, 다른 너비·테마), 현행에 없는 가짜 제목·숫자로 채운 그림은 올리지 않는다. 바뀌지 않는 부분은 현행 그림과 똑같은 실제 내용이어야 하고, 가장 확실한 만드는 법은 현행과 같은 운영 화면을 열어 그 위에서 바뀐 부분만 고쳐(견본 데이터는 테스트 데이터 자리에서) 같은 방법으로 찍는 것이다. 시안을 그리기 전에 스타일 가이드(클로드 디자인 캔버스 보드 1 — 주소는 `.spec/config.json`의 `designCanvas` — 과 `rules/viewer-ui.md`)를 먼저 읽고 그 부품·색·틀·점 모양을 그대로 쓴다. 올리기 전에 현행과 시안을 나란히 열어 틀이 같은지 직접 보고 올린다(사용자 반려: "화면이 왜 레이아웃도 없이 개판이지", "스타일 가이드도 만들어놨는데 왜 그거를 안 쓰는 거야")
   - **신규 화면**: 설계서 보기에 아직 없는 새 화면은 `isNew: true`로 올린다. 현행 그림 없이 받고, 설계 결과 칸에 "신규 화면" 이름표와 시안만 보이며 "현행과 비교" 단추가 없다. 이미 있는 화면인데 현행 그림이 없으면 설계를 올릴 수 없다
3. **승인 전에는 구현하지 않는다.** 사용자가 설계 승인(또는 설계 없음 승인)을 하면 `request impl --id N [--commit 해시]`로 구현을 기록한다. 반려되면 이유를 읽고 설계를 고쳐 다시 올린다
4. **끝낼 때**: SKILL.md "끝낼 때" 1~3(finish 통과, 스크린샷 확인)을 통과한 뒤 `request test --id N`으로 테스트를 올린다. 테스트하다 범위 밖에서 발견한 것은 `request found --id N --text "…"`(리포트로도 올라간다). 사용자가 테스트를 반려하면 같은 요청에서 고치고 다시 `request test`
5. 코드로 알 수 있는 것은 코드에서 계산한다. 사람이 적는 것은 코드로 알 수 없는 것뿐이다

## 바로 작업 (설계 승인 없이 구현하는 길)

- **쓸 수 있는 것**: 눈에 보이는 화면과 정보(데이터 항목)는 그대로이고, 잘못 동작하는 것만 바로잡는 고장 수리로 내용이 분명한 것(예: 눌려야 할 단추가 안 눌림)
- **못 쓰는 것**: 화면 모양·정보 항목·사용 흐름이 바뀌는 일, 새 기능, 규칙 문서의 정책 변경, 내용이 분명하지 않은 일
- **정하는 법**: 등록할 때 상세 내용을 사용자가 확인하고(`intake.md`), 에이전트가 제안해 사용자가 결정한다(사용자가 먼저 시켜도 된다). `request add --detail … --mode direct --reason …`. 화면·정보를 범위에 넣으면 등록이 거절된다
- **기록**: 접수를 거치지 않고 설계 없음 승인(진행 기록 "바로 작업으로 등록(설계 없음 승인으로 봄)")으로 곧바로 구현 단계가 된다. 담당 세션을 새로 만들지 않고 등록한 세션이 이어서 고친다. 구현 뒤 **테스트 승인은 그대로 받는다**(시나리오가 없으면 "테스트 없음"). 생략되는 것은 설계 승인 하나뿐이다
- **중간에 멈추는 조건**: 하다가 화면이나 정보를 바꿔야 한다고 알게 되면 멈추고 설계를 올려 정식 경로로 돌아간다

## 구현하다 막혀서 함께 고친 것

- 구현하다 다른 오류에 막혀 테스트를 진행할 수 없으면, 그 세션에서 바로 고치되 **`request also --id N --text "막혔던 일과 고친 일" [--where 화면이나 파일] [--commit 해시]`로 요청에 남긴다**. 고친 일마다 한 건이고, 크기 제한은 없다. 크기가 적당한지는 사용자가 요청 상세에서 보고 그때그때 판단한다
- 구현·테스트 단계에서만 남길 수 있다. 요청 상세의 구현 칸과 테스트 확인 칸에 "함께 고친 것"으로 보여, 사용자가 원래 기능과 같이 확인한다(승인을 막지 않고 확인표 단계도 늘지 않는다)
- **쓰지 않는 때**: 화면 모양·정보 항목·사용 흐름이 바뀌는 일이면 같이 고치지 않고 멈춰서 새 요청이나 설계로 간다(위 "바로 작업"의 중간에 멈추는 조건과 같다)

## 구현·테스트 중 설계 변경이 필요할 때 (설계 변경)

- 설계가 틀렸다는 것을 알았든, 일부러 바꾸고 싶든, 요구가 바뀌거나 늘었든, 실제 모습에 맞춰 갱신해야 하든 **같은 하나의 길**이다. 종류를 고르지 않고 변경사항만 적는다
- 사용자는 요청 상세 오른쪽 패널 맨 아래 "설계 변경"에서 "변경사항을 적어주세요" 칸에 쓰고 "설계 변경"을 누른다. 단계가 설계로 바뀐다는 확인 창이 뜨고, 확인하면 요청이 설계 다시 작성 중으로 돌아간다. 허락은 필요 없다
- 설계가 바뀌면 오류 수정이나 구현이 필요 없어질 수 있어 테스트보다 **설계 변경을 먼저 처리**한다: 테스트는 멈추고, 새 설계가 승인되기 전에는 이 요청 번호로 소스를 커밋할 수 없다(기계가 막는다)
- 담당 에이전트에게는 승인·반려와 같은 방식(결정으로 기록 → 담당 세션에 전달 → 보냄·읽음·반영 상태 카드)으로 전달된다. 에이전트는 진행 기록의 변경사항을 읽고 설계를 고쳐 `request design`으로 다시 올린다
- **에이전트는 사용자의 요구 없이 설계를 바꾸지 않는다.** 에이전트용 `request redesign --id N --quote "사용자가 한 말" --reason "변경사항"`은 사용자가 설계 변경을 요구하며 한 말(2글자 이상)을 그대로 적어야만 기록되고, 그 인용은 진행 기록에 남는다. 인용 없이 에이전트가 스스로 설계를 바꾸는 길은 없다(소스의 설계 주석을 직접 고치는 것을 기계로 막는 일은 하지 않으니 규칙으로 지킨다)
- 설계는 덮어쓰지 않고 판으로 쌓는다: 설계 변경이 시작되면 그때까지의 설계가 이전 설계(설계 1판…)로 남고 시안 그림도 판별로 따로 저장된다. 요청 상세의 설계 칸에서 이전 설계와 변경사항, 승인 시각이 보인다. 설계 변경도 처음 설계와 똑같이 사용자가 승인하며, 반려하면 고쳐 다시 올린다
- 새 설계 승인 뒤 구현하고 `request test`를 다시 올릴 때 확인표를 새 설계 기준으로 맞춘다: 제목과 확인 기준이 그대로인 단계의 체크는 두고, 바뀌었거나 없어진 단계의 체크는 풀린다. 범위의 시나리오가 바뀌면 `request scope`로 다시 연결한다
- 구현·테스트 단계에서만 쓴다(설계 단계는 그대로 설계를 고쳐 올린다). 상세에 "설계 변경 n회"가 보인다

## 테스트는 테스트 데이터로 한다는 표시

- 테스트 승인 대기인 요청의 오른쪽 "사용 시나리오 테스트" 패널 맨 위에 "이 테스트는 테스트 데이터로 합니다 · 운영 데이터가 아닙니다" 안내가 보이고, 시나리오 옆 단추는 "테스트 데이터로 첫 화면 열기"다. 눌러 보기 전에 테스트 데이터로 한다는 것을 알게 한다
- 그 단추는 **운영 설계서 보기의 화면 설계서**를 새 창으로 연다. 안쪽 "실제 화면"에만 테스트 서버의 앱 화면이 뜨고, 그 위에 "테스트 데이터로 보는 화면입니다 · 운영 데이터가 아닙니다" 띠가 한 줄 따로 잡혀 안쪽 화면은 그 아래로 밀리고(아무것도 가려지지 않는다), 가장자리에 테두리가 둘린다. 바깥 위쪽 줄·코멘트 창·승인·반려는 운영 그대로다
- 이 모습은 주소에 테스트 경로 표시(요청 번호·시나리오)가 있고 그 요청이 지금 테스트 단계일 때만 나온다. 평소 화면 메뉴에서 연 화면 설계서, 설계·구현 단계, 요청 상세 "범위" 칸의 "첫 화면 열기", 테스트 환경이 없는 프로젝트는 운영 앱을 띠 없이 보인다
- 프로젝트 설정 `.spec/config.json`의 `testData.reviewUrl`에 테스트 데이터로 띄운 앱 주소를 적으면 켜진다. dev-method는 운영과 별도 서버로 띄우며 포트는 달라도 이름으로 구분되게 `http://test.localhost:5391/__spec/`다. 테스트 서버가 꺼져 있으면 화면을 열 때 자동으로 켜고, 요청이 바뀔 때마다 요청 파일을 테스트 자리 복사본에 맞춘다. 별도 앱이 있는 프로젝트는 그 앱의 테스트 서버 주소를 적는다
- 테스트 서버의 화면 안(복사본에만 기록되는 곳)에서는 승인·반려·설계 변경 단추와 코멘트 창의 승인·반려·보내기를 숨기고 "운영 요청 상세에서 한다"고 안내한다
- 에이전트는 시나리오마다 정상·경계·오류 데이터를 테스트 자리에 실제로 채우고 `testdata seed`로 만든 방법과 캡처를 남긴다(정상이 없으면 `request test`가 막힌다)

## 기계가 막는 것

- **승인 전 소스 커밋**: 설계 승인 전(접수·설계 작성·승인 대기·반려)인 요청 번호로는 `.spec/`·문서(.md) 밖의 소스를 커밋하지 못한다(commit-msg 훅)
- **승인보다 앞선 커밋**: `request impl --commit 해시`는 그 커밋 시각이 설계 승인보다 앞서면 구현 기록으로 받지 않는다
- **finish 실패**: `request test`는 가장 최근 finish(`.spec/finish.json`)가 통과이고 그 뒤 소스가 바뀌지 않았을 때만 받는다

## 사용자가 하는 일 (설계서 보기 "관리")

- 설계 승인: 정보 변경과 화면 디자인을 확인(체크 두 개)하고 승인하거나, 이유를 한 줄 적어 반려한다. "설계 없음"도 사용자가 승인한다
- 겹치는 요청이 있으면 끝나는 순서를 정한다("#12 먼저")
- 테스트 승인: 요청의 사용 시나리오 확인표를 실제 화면에서 눌러 보고 체크한 뒤 승인하거나 반려한다. 시나리오가 없으면 "테스트 없음"으로 승인할 수 있다
- 승인·반려·순서·체크는 설계서 보기 서버가 받는다. 에이전트용 명령은 반려·순서·체크를 할 수 없다. 승인만은 아래 "대화에서 한 승인"으로 기록할 수 있다

## 대화에서 한 승인

- 사용자가 시안이나 설계를 대화에서 승인했으면("그대로 확정", "진행해" 등) 그 말을 요청의 승인으로 가져간다. 에이전트가 `request design`으로 설계를 올린 뒤 `request approve-design --id N --quote "사용자가 한 말"`로, 테스트도 같은 식으로 `approve-test --quote`로 기록한다
- 인용은 **그 요청에 대한 사용자의 말만** 쓴다. 일괄 지시나 다른 요청의 말을 인용해 승인하지 않고, 방금 구현을 끝낸 요청의 테스트는 사용자가 확인하기 전에 승인하지 않는다
- 설계를 올릴 때 화면 변경은 현행 그림(before)과 변경 후 그림(after)을 함께 올린다(현행이 없으면 "현행과 비교해서 보기"가 비어 사용자가 비교하지 못한다). 올린 뒤 승인 화면과 비교 화면을 직접 열어 현행과 변경 후가 모두 읽히는지 확인하고 나서 승인을 요청한다
- 인용(사용자가 한 말 그대로)이 없으면 기록되지 않는다. 인용은 요청 상세의 진행 기록에 그대로 보인다. 사용자가 승인하지 않은 것을 에이전트가 승인하지 않는다(반려도 이 명령으로는 못 한다)

## 사용자 결정이 담당 세션에 전달되는 방법

- 사용자의 승인·반려·순서 정하기는 요청 파일에 기록된다. 담당 세션은 감시기 없이 **훅**(`spec.mjs inbox`, `./install.sh agent-hook <프로젝트>/.claude/settings.json`으로 등록)으로 받는다
- 세션이 `request agent --id N`을 실행하면 훅이 그 세션을 요청 N의 담당으로 적는다(요청을 접수만 하는 `request add`는 담당으로 적지 않는다. 접수한 세션이 담당이 되면 시작할 때 담당 세션이 만들어지지 않는다)(`.spec/sessions.json`, 커밋하지 않음). 그 뒤 사용자가 말을 걸 때와 도구를 쓴 뒤에 새 결정이 있으면 "이어서 할 일"과 함께 알려 준다. 세션이 완전히 쉬고 있으면 사용자가 `claude attach <이름>`으로 들어가 말을 걸 때 전달된다
- **담당 세션은 서버가 만들고 깨운다**(`src/session.ts`·`src/wake.ts`, 기본 꺼짐). 프로젝트 설정 `.spec/config.json`에 `"wake": true`를 쓰면 다음이 켜진다. ① **시작**: 접수된 요청을 사용자가 화면의 "시작" 단추나 `request start --id N`으로 시작하면 그 요청만 맡는 새 세션을 `claude -p 글 --session-id 새번호`로 만들고(`.spec/sessions.json`에 바로 적음), 그 세션이 담당을 등록하고 설계를 써서 올린 뒤 승인 대기에서 멈춘다. 담당이 이미 있으면 새로 만들지 않는다(방금 만들어 아직 담당을 등록하지 못한 "시작 중" 세션도 30분 안에는 있는 것으로 본다). 시작은 깨움 줄을 서지 않고 바로 하며, 시작한 지 10분이 넘도록 담당 등록도 기록도 없으면 서버가 1분 점검에서 같은 세션으로 한 번 다시 시작하고, 그래도 안 되면 진행 기록에 "담당 세션 시작이 끝나지 않음"을 남긴다. ② **결정**: 사용자가 승인·반려·순서를 정하면 담당 세션이 지금 일하는 중인지 `claude agents --json`으로 보고, 일하는 중이 아니면(VS Code나 터미널에 열어 두고 기다리는 세션, 일을 마치고 쉬는 세션, 오래된 세션) 그 세션에 글을 보낸다. 1시간 넘게 쉬어 캐시가 식었거나 대화 기록이 500KB 넘게 클 때만 먼저 `claude -p "/compact" --resume 세션`으로 압축한 뒤 "요청 파일과 `todo` 명령을 읽고, 결정된 그 일만 하고 끝나면 멈추세요"를 보낸다(압축만으로는 움직이지 않아 두 번 부르고, 압축이 실패해도 두 번째는 보낸다). 깨움은 같은 세션에는 한 번에 하나씩, 서로 다른 세션은 동시에 3개까지 돈다. 테스트 승인처럼 완료로 닫는 결정과 이미 완료·취소된 요청은 깨우지 않고 전달 기록도 만들지 않는다. 사용자가 담당 세션의 지난 일을 볼 때는 세션에 접속하지 않고(일하는 세션에 접속하면 입력으로 받아들여져 멈춘다) 요청 상세 "대화 보기"를 쓴다(`src/conversation.ts`, 세션 기록 파일을 읽기만 한다). 일하는 중인 세션은 서버가 같은 대화에 끼어들지 않고 위의 훅에 맡긴다(곧 도구를 쓰므로 그때 전달된다. 기다리는 세션은 훅이 움직일 수 없어 직접 보낸다). 완료로 닫는 테스트 승인과 이미 완료·취소된 요청은 깨우지 않는다. 깨움은 같은 세션끼리만 차례로 하고, 서로 다른 세션은 동시에 3개까지 돈다. 결정이 전달되지 않았으면 `request wake --id N`으로 마지막 결정을 다시 보낸다(일하는 중인 세션에도 보낸다). 담당 세션이 한 번도 없었으면 새로 만들어 그 일을 맡긴다. 세션은 읽기·고치기·`node`·`npm`과 그 일의 `git add`·`git commit`을 쓸 수 있고, 위험한 git은 차단 훅이 막는다. **비용**: 만들거나 깨울 때마다 claude 결과에서 토큰과 비용을 읽어 `.spec/session-costs.json`(커밋하지 않음)에 적고(`cost` 명령), 요청 상세 "맡은 에이전트" 칸에 합계와 횟수가 보인다. 결과는 `.spec/wake.log`에 남고, 시작·깨우기가 실패해도 사용자의 시작·결정은 그대로 처리된다
- 에이전트는 알림이 올 때까지 기다리지 않고, 승인이 필요한 단계에서는 "승인 대기"라고 사용자에게 알리고 멈춘다

## 기록

- 요청 하나가 `.spec/requests/<번호>.json` 파일 하나다(진행 기록, 설계, 테스트 확인, 구현 커밋). 설계 그림은 `.spec/shots/`에 저장된다. 둘 다 커밋한다
- 화면 승인과 화면 상태(개발 중·테스트 요청·승인됨)와 메모는 없앴다. 화면 설계서의 히스토리는 그 화면을 바꾼 요청(설계 승인, 구현 커밋, 테스트 승인)과 요청 번호 없이 남은 변경을 보인다
