# 화면과 컴포넌트

- 화면 = 라우터에 등록된 라우트. 라우트 컴포넌트 위에 `@screen 이름`, `@route`, `@why`(존재 이유), `@does`(사용자가 하는 일 | 확인 기준), `@to`(나가는 길)를 쓴다. 문법은 `rules/tools.md`
- 설계서 보기가 실제 화면을 끼워 넣으므로 `@route`가 앱의 실제 주소와 맞아야 한다. 주소 변수가 있으면 `@sample`로 실제 주소를 준다
- 라우터 밖 화면(모달, 시트)은 라우트로 올린다. 안 되면 임시 `@screen`을 쓰고 경고로 남긴다
- 화면 이동은 타입 있는 라우트 정의 한 곳(`ROUTES` 객체)과 라우트 도우미(`toPath('이름', 값)`) 호출로 쓴다. 도구(`nav.mjs`)가 이 호출과 `to="/주소"`, `navigate("/주소")`를 읽어 `@to`와 대조한다. 주소를 문자열 변수로 조립하면 읽히지 않는다. 넘기는 값의 타입을 쓴다. 이동 약속 타입(`RouteParams` 등)은 JSDoc에 `@nonInfo`를 단다
- 화면 안 컴포넌트는 `@spec 이름`과 `@anchor`, 존재 이유를 쓴다. 이벤트는 `@on 이벤트: 효과`로 쓴다
- 이벤트 핸들러는 이름 있는 함수로 만든다(도구가 동작 이름을 읽는다)

- 눌러야 나타나는 컴포넌트(시트, 탭 안 내용, 메뉴, 편집기)도 다른 컴포넌트와 똑같이 `@spec`과 `@anchor`를 쓴다. 소스에 "눌러야 나타남" 같은 표시를 따로 쓰지 않는다. 끝낼 때 확인(`finish.mjs`)이 화면의 버튼·탭·`summary`를 직접 눌러 보며(최대 두 번 연달아) 나타나는 순서를 찾아 `.spec/reveal.json`에 기록하고, 설계서 보기의 컴포넌트 카드가 "눌러야 나타난다 — A → B를 누르면"과 "열어서 보기"를 보여 준다
- 그래도 못 찾으면 진짜 문제다: `@anchor` 선택자가 틀렸거나, 데이터·조건에 따라서만 나타나는 요소다. 선택자를 고치거나 눌러서 나타나게 만든다
