# 변경을 요청받았을 때 (채널은 자유, 기록은 반드시)

- 요청 채널은 에이전트와의 대화다. 변경은 크기를 나누지 않고 요청마다 담당 세션이 처리하며, 사용자는 설계 승인과 테스트 승인 두 문턱에서 확인한다
- 변경 요청을 받으면 가장 먼저 요청을 등록한다. 등록 전에 합칠 요청이 있는지 찾는 접수 절차를 거친다(`rules/intake.md`). 합칠 것이 없으면 `request add …`. 요청 하나가 화면 몇 개를 건드려도 하나로 다룬다. 요청 번호가 모든 일의 열쇠다
- 요청의 흐름과 사용자 승인, 에이전트가 쓰는 명령은 `rules/approval.md`
- 작업 중이나 정기 점검에서 에이전트가 발견한 것은 바로 고치지 않고 리포트로 올린다: `report add --title "…" [--detail …] [--label 보안] [--from "주기 점검"] [--where 화면1,정보1] [--recommend registered|kept|analyze --why "추천 이유 한 줄"]`. 올릴 때 추천(요청으로 처리 / 그냥 둠 / 더 분석)과 이유를 꼭 붙여, 사용자가 소스를 열지 않고 판단하게 한다. 사용자가 설계서 보기 "관리 › 리포트"에서 요청으로 처리 · 그냥 둠 · 더 분석 중 하나를 고른다. 요청으로 처리되기 전에는 고치지 않는다. 사용자가 더 분석을 맡기면(`todo`의 "리포트 확인 중") `report show`로 의견을 읽고 조사한 뒤 `report note <번호> --text "조사한 사실" [--recommend …]`로 결과와 새 추천을 붙인다. 도구가 못 읽어서 생긴 것은 프로젝트 결정에서 빠져 접힌 줄로 모인다. 리포트마다 번호(#31 같은)가 있고, 사용자가 "리포트 #31 설명해 줘"처럼 번호로 물으면 먼저 `report show 31 --src <소스 폴더>`로 근거·소스 위치·관련 화면을 읽고 그 내용에 소스를 더 확인해 답한다
- 우리가 만든 말(설계 승인, 겹침 등)은 용어집에 둔다: `glossary add --term "…" --meaning "쉬운 설명" [--uses 쓰이는 곳,…]`. 테스트를 올릴 때와 주기 점검 때 새로 생긴 말이나 바뀐 말을 반영한다. 일반 개발 용어는 넣지 않는다
- 모든 변경의 커밋 메시지에 `요청 #번호` 줄을 쓴다. 이력은 이 커밋에서 도구가 모은다. **번호가 없거나 등록되지 않은 번호면 커밋이 막힌다**(git commit-msg 훅, `./install.sh spec <프로젝트>`로 연결. 병합·되돌리기는 예외, 요청이 하나도 없는 프로젝트는 통과). 이미 번호 없이 남은 변경은 요청 목록의 "요청 없는 변경"에 올라온다

## 화면 코멘트

- 사용자는 설계서 보기의 어느 화면에서든 오른쪽 아래 "코멘트" 단추로 부품·영역·화면 전체를 골라 코멘트를 남긴다. 코멘트는 `.spec/comments.json`에 쌓이고(커밋하지 않는다) 에이전트가 읽어 간다.
- 작업을 시작하거나 사용자가 "코멘트 봐 줘"라고 하면 `comment list --src <소스 폴더>`로 답을 기다리는 것을 보고, `comment show <번호> --src …`로 대상(화면·부품·소스 위치·리포트 번호·캡처 파일)과 대화를 읽는다. 소스를 직접 확인한 뒤 `comment reply <번호> --text "답" --refs 파일:줄,… --src …`로 답한다. 확인한 소스 위치를 --refs에 적는다.
- 코멘트가 일이 되려면 사용자가 "이 일을 요청으로 만들기"를 눌러야 한다. 에이전트가 코멘트만 보고 코드를 고치지 않는다.

## 할 일 정하기 (요청을 바로 설계하지 않는다)

- 요청을 받으면 `request add`로 접수만 한다. 접수한 요청은 **접수** 상태이고, 바로 설계를 쓰지 않는다. 우선순위에 따라 설계할지 구현할지를 할 일을 정할 때 정한다
- 사용자가 "할 일 뭐있지", "할 일", "승인 대기", "뭐 남았지"처럼 물으면 `todo --src <소스 폴더>`로 요청 목록·코멘트·리포트를 읽어 그대로 정리해 보이고, "제안 순서"를 확인받는다. 이 명령은 읽기만 한다
- 정리할 때 내 차례(사용자가 승인할 것)는 한 건씩 무엇이 바뀌었고 어디서 확인하는지 알려 승인을 요청한다. 사용자가 구두로 승인하면 그 요청에 대한 그 말만 인용해 `approve-design`·`approve-test --quote`로 기록한다. 다른 요청이나 일괄 지시를 인용해 승인하지 않는다
- 순서가 정해지면 접수된 요청은 사용자가 화면의 "시작" 단추나 `request start --id N`으로 시작한다(설정 `wake`가 켜져 있으면 시작 글이 outbox에 적히고 메신저 세션이 `claude --bg --session-id`로 그 요청을 맡는 새 담당 세션을 만든다, `rules/approval.md`). 설계 승인된 요청은 구현하고, 구현을 마치면 테스트를 올린다. 사용자 승인이 필요한 곳에서만 멈춘다

## 메인 세션과 담당 세션

- 메인 세션은 접수, 할 일 정리(`todo`), 상태 기록, 담당 세션 열기만 한다. 구현과 설계는 요청마다 담당 세션이 한다. 사용자가 요청을 시작하면(화면의 "시작" 단추, `request start`) 시작 글이 outbox에 적히고 메신저 세션이 그 요청의 담당 세션을 만들어 보낸다(서버는 어떤 경우에도 `claude -p`로 세션을 만들거나 글을 보내지 않는다. `wake` 설정이 꺼져 있으면 메인 세션이 담당 세션을 직접 연다)
- 담당 세션에 넘길 때는 **그 요청 하나에 필요한 것만** 준다: 요청 번호와 원문, 증상이나 목표, 읽을 파일, 지킬 것. 다른 요청의 상태나 메인 세션의 대화·규칙 이야기를 넣지 않는다. 세션을 나누는 이유가 한 요청에만 집중하게 하려는 것이기 때문이다
- 담당 세션은 `request agent --id N --name …`으로 담당을 등록하고, 승인은 하지 않으며(사용자 몫), 화면 변경이 필요하면 멈춰서 시안을 요청한다
- 담당 세션은 일을 시작하기 전에 먼저 `request whoami --id N`으로 "내가 이 요청의 묶인 원본 담당인가"를 확인한다(판단은 도구가 한다). "복사본"이라고 나오면 아무 일도 하지 않고 멈춘다: 워크트리·브랜치·커밋·요청 상태 변경은 훅이 기계로 거절하고, 거절은 요청에 '복사본이 거절됨' 한 줄로만 남는다(붉은 막힘이 아니다). "맞추는 중"이면 잠시 뒤 다시 확인한다. 원본이 맞는데 어긋난 것이면 사용자·메인 세션이 `request adopt --id N --session 세션번호`로 원본을 지정한다. 담당을 띄우는 것은 서버(ownerUp) 한 곳이고, 서버의 1분 점검(reconcile)은 위 장치가 뚫려 담당·메신저가 겹쳤을 때만 정리한다.
