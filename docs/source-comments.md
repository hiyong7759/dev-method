# 소스를 쓰거나 고칠 때

목적: 구현된 뒤에는 설계문서 없이 **존재 이유 주석과 코드만 보고** 다음 에이전트가 "적정하게 구현됐다/덜 됐다"를 판정할 수 있게 하는 것. 히스토리는 커밋에서 찾게 해 주석이 시간이 지나도 커지지 않게 하는 것.

## 원칙

- 목표: 승인된 설계가 구현되면 그 내용이 존재 이유 주석 + 코드로 남아, 그 뒤로는 설계문서 없이 소스만으로 현행을 알 수 있는 것
- 문서와 주석은 현재 기준만 쓴다(예전과의 비교·이관 표시를 넣지 않는다)
- 규칙은 코드에 묻지 않고 프로그램이 실제로 읽는 선언형 설정 파일 한곳에 둔다

## 존재 이유 주석

- 파일 헤더 = 이 파일이 왜 있나 (몇 줄). 컴포넌트(함수·클래스·설정 묶음) 바로 위 = 그것이 왜 있나
- 존재 이유는 개발자, 기획자, 일반인 누구나 이해하게 쉬운 말로 쓴다(사용자가 무엇을 보고 하는지, 왜 필요한지 먼저)
- 새 컴포넌트를 만들면 존재 이유 주석을 함께 쓴다. 이유가 달라졌을 때만 고친다
- 동작 설명을 주석으로 반복하지 않는다(어떻게는 코드가 말한다). 이유와 코드가 어긋나면 둘 중 하나를 고친다
- 히스토리(예전엔 A였다가 B로)와 기각은 주석에 쓰지 않는다. 커밋에 있다
- 출처: 외부 근거(법령, 표준, 논문, 측정 데이터)는 이름을 적는다. 사용자 결정은 사용자가 그 내용을 직접 말한 것에만 `(사용자 결정)`을 단다
- 숫자 상수(문턱, 시간, 비율)에는 근거를 적는다. 모르면 지어내지 말고 "근거 없음"이라 적는다
- 측정값에는 날짜를 붙인다(`2026-10-14 측정`). 다시 재지 못한 옛 값은 그렇다고 표시한다
- 주석을 달 수 없는 JSON은 그 묶음의 `about` 문구가 존재 이유 주석이다
- 주석이 20줄 안팎을 넘으면 파일이 너무 많은 일을 한다는 신호로 보고 나누기를 제안한다
