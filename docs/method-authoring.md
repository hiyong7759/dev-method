# 정책을 어디에 둘까

CORE.md는 모든 프로젝트에서 늘 읽히므로 핵심만 둔다. 자세한 내용은 별도 장치로 나눈다. 모든 경우를 지금 식별할 수 없으니 쓰면서 고친다.

## 장치 고르기

- **매 작업에 해당하는 원칙** → CORE.md 한 줄. 이유·예·절차는 쓰지 않는다
- **특정 순간에만 필요한 깊이** → `docs/`에 문서 하나, CORE에 "그 순간일 때: 문서 경로를 읽는다" 포인터 한 줄. 문서 하나는 순간 하나만 다룬다
- **기계적으로 가려지는 것**(비밀번호, 위험한 git 명령) → 훅·스크립트. 문장으로 부탁하지 않는다
- **훅 설치본이나 참고 구현 같은 파일 묶음이 딸린 것** → 스킬. 스킬은 설명이 매 턴 컨텍스트에 올라가므로 이 경우에만 쓴다

## 포인터 쓰는 법

- 단어가 아니라 상황으로 쓴다. "새 세션 문구를 쓸 때"보다 "작업을 다른 창·세션에서 이어가게 할 때". 단어로 쓰면 비슷한 단어에 걸리거나 단어 없는 요청을 놓친다
- 경로는 절대 경로로 쓴다 (다른 프로젝트에서도 읽혀야 한다)
- 포인터가 늘어도 CORE에는 한 줄씩만 더한다. 문서가 길어지면 문서 안에서 제목으로 나눈다

## 쓸 때 지킬 것

- 한 사례에만 강한 규칙은 다른 사례를 방해한다. 사용자 선호가 아니라 에이전트가 사건 하나를 겪고 만든 대응이면 CORE에 넣지 않는다
- 방법론·도구의 근거는 한 프로젝트(특히 막 시작한 것)가 아니라 성숙도와 구조가 다른 둘 이상을 보고 잡는다. 한 사례에서 얻은 결론은 "그 프로젝트에서는"이라고 범위를 밝힌다
- 미래 조건("~가 생기면 다시 정한다")은 문장으로 두지 않는다. 다시 볼 시점은 포인터가 걸리는 순간이나 날짜 있는 메모에만 둔다
- 히스토리·기각·출처 인용·시험 결과는 CORE와 docs가 아니라 커밋 메시지에 남긴다
- 안 읽히거나 안 지켜지면 내용이 아니라 장치를 바꾼다
- 바꾸는 것은 사용자 확인 뒤에 한다
