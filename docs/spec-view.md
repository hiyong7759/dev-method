# 화면·정보·로직을 만들거나 고칠 때 (설계서 보기)

목적: 소스가 곧 설계서가 되게 한다. `skills/spec-view` 도구가 소스에서 화면 흐름·정보 흐름·화면 설계서를 읽어 보여주므로, 아래를 지키면 설계서를 따로 쓰지 않는다.

## 원칙

- 코드에 이미 있는 것(정의, import, 읽기·쓰기)은 도구가 읽는다. 사람(에이전트)이 쓰는 것은 코드에 없는 것(존재 이유, 근거, 약속, 동작의 의미)뿐이다. 같은 사실을 두 번 쓰지 않는다
- 존재 이유는 에이전트가 쓰고 사용자가 검토한다. 처음 방향은 사용자가 주거나 에이전트가 제안해 승인받는다
- 타입 선언이 가능한 언어를 기본으로 한다
- 도구가 못 읽는 구조는 읽히게 고친다. 정 안 되면 임시로 선언하되 경고로 남긴다. 선언은 도구가 코드와 대조한다

## 도구가 읽는 것과 읽히게 쓰는 법

도구는 `skills/spec-view`의 `extract.mjs`(주석 태그)와 `analyze-ts.mjs`(TypeScript)다. 에이전트는 아래 모양으로 써야 도구가 읽는다.

도구가 지금 읽는 것:

| 알아내는 것 | 읽는 방식 | 이렇게 써야 읽힌다 |
|---|---|---|
| 정보 목록, 필드 | TypeScript 언어 서비스로 export된 `interface`·`type`·`enum`을 모은다 | 정보는 export된 이름 있는 타입으로 정의한다 |
| 필드를 읽고 쓰는 곳 | 필드 단위 참조 분석(읽기·쓰기 구분), 쓰는 파일·영역 | 파생 타입은 `Pick`·`Partial`·`Omit`으로 만들고, 필드 이름 문자열은 `keyof`로 묶는다 |
| 정보 필드의 존재 이유 | 정의 바로 위 주석 | 필드마다 바로 위에 `/** 한 줄 */`로 쓴다 |
| 화면·컴포넌트·로직의 존재 이유 | 주석 태그 `@screen`·`@spec`·`@why`·`@basis`·`@contract`·`@anchor` | 블록 주석 안에서 태그로 시작하는 줄을 쓰고, 값이 길면 다음 줄에 이어 쓴다 |
| 틀릴 수 있는 곳 | 쓰기·읽기가 안 보이는 필드는 같은 이름의 다른 정의와 문자열 참조를 근거로 "후보"로 표시한다 | 같은 정보를 손으로 다시 정의하지 않는다 |

```ts
export interface TripItem {
  /** 같은 날 안에서 일정의 순서와 이동 시각을 알리려고 */
  assignedTime?: string;
}
```

```tsx
/**
 * @screen Day 상세
 * @why 하루 일정을 시간 순서로 보고, 예약 여부와 시각을 바로 고치게 하려고
 */
```

도구가 아직 못 읽는 것(화면 목록과 이동, 이벤트와 동작, `@on`, `@ref`, `@does`, 메모, 화면 상태와 승인 기록)은 주석 태그로 임시 선언한다. 읽게 되면 이 표로 옮기고 임시 선언은 경고로 지운다. 이 표는 도구를 고칠 때 함께 고친다.

## 메타정보 — 있는 것과 없는 것이 섞여도 혼란이 없게

- 메타정보 = 소스 주석에 쓰는 존재 이유, 근거, 약속, 동작이다
- 필수 메타정보는 존재 이유다(정보 필드, 화면, 컴포넌트, 로직 모두). 이벤트 핸들러가 있는 컴포넌트는 `@on`도 필수다
- 선택 메타정보는 근거와 약속이다. 있을 때만 쓴다
- 도구는 필수 메타정보가 비면 "미작성"으로 표시하고 경고에 올린다. 선택 메타정보가 비면 아무것도 표시하지 않는다. 그래서 화면에 "미작성"이 보이면 항상 채워야 할 곳이다
- 새로 만드는 것에는 필수 메타정보를 함께 쓴다. 기존 것에 필수 메타정보가 비어 있으면 그 작업 범위에서 채운다

## 정보

- 정보 = 이름 있는 데이터 정의(타입·클래스·스키마) 한 곳. 필드마다 존재 이유를 단다(정말 필요한 정보인가의 판단 기준). 존재 이유 없는 필드는 정리 후보다
- 파생 타입은 원본에서 만든다(`Pick`, `Partial`, `Omit`). 필드 이름을 문자열로 쓸 때는 `keyof` 타입으로 묶는다
- 외부에서 들어오는 정보(API, DB)는 스키마에서 타입을 만든다
- 저장·네트워크·이벤트 접근은 타입 있는 얇은 한 층으로 모은다
- 다른 정보를 가리키는 값은 id 필드로 드러낸다. 값으로만 가리키는 약한 연결은 필드 주석에 `@ref 대상.필드`로 쓴다

## 화면

- 화면 = 라우터에 등록된 라우트. 라우트 컴포넌트 위에 `@screen 이름`과 존재 이유, 사용자가 하는 일을 쓴다
- 라우터 밖 화면(모달, 시트)은 라우트로 올린다. 안 되면 임시 `@screen`을 쓰고 경고로 남긴다
- 화면 이동은 타입 있는 라우트 정의 한 곳에 두고, 넘기는 값의 타입을 쓴다
- 화면 안 컴포넌트는 `@spec 이름`과 `@anchor`, 존재 이유를 쓴다. 이벤트는 `@on 이벤트: 효과`로 쓴다
- 이벤트 핸들러는 이름 있는 함수로 만든다(도구가 동작 이름을 읽는다)

## 로직

- 화면에 없는 모듈도 `@spec`을 쓴다. 제목은 무엇을 맡는지 보이게 쓰고, 받는 것·내는 것은 타입으로 드러내며, 다른 곳과의 약속은 `@contract`에 쓴다

## 승인

- 화면 상태는 개발 중, 테스트 요청, 수정 필요, 승인됨, 승인 후 변경됨이다
- 에이전트는 작업을 끝낼 때 자체 점검(경고 0, 화면이 열리는 것 확인)을 통과하면 화면을 "테스트 요청"으로 기록하고, 확인 방법을 메시지로 남긴다
- 사용자는 확인 목록(화면 메타정보 `@does`에 쓴 "사용자가 하는 일")을 실제 화면에서 눌러 보고, 문제는 오류 메모로 남기거나 승인한다. 승인은 사용자만 한다
- 승인하면 승인한 사람·시각·소스 버전이 기록된다. 그 뒤 화면의 소스가 바뀌면 자동으로 "승인 후 변경됨"이 되어 다시 확인을 받는다

## 변경을 요청받았을 때 (채널은 자유, 기록은 반드시)

- 요청 채널은 설계서 보기의 메모(컴포넌트, 영역, 빈 영역)와 에이전트와의 대화다. 어느 채널이든 같은 절차를 탄다
- 작은 변경(오류 수정, 메타정보가 바뀌지 않는 부분 수정)은 바로 구현한다
- 큰 변경(개선, 개편)은 존재 이유·사용자가 하는 일·정보 정의 중 하나가 바뀌는 변경이다. 에이전트가 먼저 영향 범위, 바뀌는 메타정보, 단계를 계획으로 제안하고, 사용자가 계획을 승인한 뒤에 구현한다
- 대화로 요청받은 변경도 에이전트가 요청 기록(채널, 요약)을 메모와 같은 형식으로 남긴다
- 모든 변경의 커밋 메시지에 `요청:` 줄(채널과 요약)을 쓰고, 큰 변경이면 `성격: 개선` 또는 `성격: 개편` 줄을 쓴다. 이력은 이 커밋에서 도구가 모은다

## 읽고 채우는 순환

- 이 순환은 화면·정보·로직의 소스를 만들거나 고치는 작업에만 적용한다. 질문, 조사, 기록 정리에는 적용하지 않는다
- 읽는 것은 작업 범위(그 화면, 그 정보)의 요약과 경고뿐이다. 프로젝트 전체를 읽지 않는다. 메모는 대기·응답 필요 건이 있을 때만 읽는다
- 작업을 시작할 때 코드를 처음부터 분석하지 말고, 도구가 만든 요약(`extract.mjs <폴더>`의 JSON, 정보 분석 결과)과 경고 목록을 먼저 읽는다
- 사용자가 설계서 보기에 남긴 메모 중 대기·응답 필요 건이 작업 범위에 있으면 읽고, 코드와 대조해서 답한다. 반영한 메모에는 응답과 커밋 해시를 남기고 "반영됨"으로 바꾼다. "확인 완료"는 사용자만 바꾼다
- 작업을 끝낼 때 작업 범위의 빈 필수 메타정보(경고 목록)을 채운다. 채우는 내용은 코드로 확인한 것만 쓴다
