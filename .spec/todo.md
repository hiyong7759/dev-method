# 지금 해야 할 일 (컴팩팅 뒤 이 파일부터 읽고 시작한다)

이 프로젝트(dev-method)의 "설계서 보기" 도구를 이 프로젝트 자신이 관리한다. 소스는 맨 위 `src/`(TypeScript), 스킬은 `skills/spec-view/`(안내와 입구 `spec.mjs`). 서버는 `node skills/spec-view/spec.mjs open .` 으로 켜고 http://localhost:5291/ 로 본다. 마지막 커밋은 `git log`로 확인.

## 작업 규칙 (어기면 사용자가 화낸다)

- **질문에는 답만 한다.** 고치라고 하기 전에는 코드·파일을 바꾸지 않는다. 답을 맨 앞에 쓴다
- **화면을 만들거나 고치기 전에 클로드 디자인 시안을 먼저 보여 주고 승인받는다.** 시안에 없는 것을 구현하지 않는다. 시안과 다르게 구현하지 않는다
- **새 화면 요소를 만들기 전에 기존 화면이 같은 것을 어떻게 하는지 먼저 확인하고, 공통 부품·UI 규칙을 따른다.** 같은 개념(거르기, 확인 필요, 사이드 패널, 단추)은 한 가지 방식으로만 만든다
- 단계마다 작게 보여 주고 확인받는다. 기준을 사용자가 안 줬으면 내가 정하지 말고 먼저 묻는다
- 길게 늘어놓지 않는다. 큰 방향부터 짧게. 한국어, 쉬운 말, 코드 용어는 풀어서

## 지금 순서 (시안 승인됨, 구현 단계)

시안(캔버스 보드 1~15, 밝기 단추 포함)은 승인됨. 이제 시안에 맞춰 구현한다. 작게 보여 주고 확인받는다.

- 끝남: 시안 정리와 스타일 가이드(캔버스 버전 22), 색 이름표 + 다크·라이트·시스템 밝기 단추(995f096), `skills/spec-view/rules/viewer-ui.md`
- 다음: ① `src/viewer/util.ts`로 공통 부품 뽑기(chip, tag, btn, rv, side-list, ph 머리, sidepanel) ② 화면 맞추기: 상단 바(내 차례만, 승인 대기·전달 전 메모 이름표 제거) → 사용 흐름(왼쪽 도메인 목록+위쪽 칩+rv+확인 필요 패널) → 정보 흐름(왼쪽 도메인 목록, 판단 박스를 확인 필요 패널로) → 머리 통일 → 화면 탭 개요·현행·히스토리 → 요청 목록 → 리포트·용어집 화면
- 사용자에게 물을 것(내가 정하지 않는다): "의도한 것"의 기록 자리(소스 주석인지 `.spec` 목록 파일인지), 커밋 007114b 유지·되돌림, 사용 흐름 오른쪽 패널에 ✕·설명 줄을 더할지, 정보에 도메인이 없어서 "쓰는 화면의 도메인에서 계산"해도 되는지

## 지금 구현과 시안·일관성이 어긋난 곳 (정리 대상)

- 사용 흐름 거르기: 시안은 왼쪽 도메인 목록, 구현은 위쪽 칩(내가 멋대로 바꿈). 정보 흐름은 위쪽 칩. **기준을 사용자가 정해야 한다**(도메인이 늘어나면 왼쪽 목록, 구분이 3~4개 고정이면 위쪽 칩이라는 의견은 드렸음)
- 확인 필요: 정보 흐름은 필드 검사(판단 박스, 필터 칩), 사용 흐름은 모델 `notes`(시나리오 단추 + 오른쪽 패널). 같은 개념인데 방식이 둘이다 → 한 곳에서 한 방식으로 만들고 화면은 자기 것만 보여 주기
- 시안 없이 만든 것: 시나리오의 확인 필요 단추·패널, 정보 흐름 필터 칩·"확인 필요" 탭, 판단 박스, 정보 상자의 확인 표시
- 공통 부품: `src/viewer/util.ts`에 `filterChips`만 있다. 패널·단추·칩은 화면 파일마다 따로

## 이미 정한 방향 (바꾸려면 사용자 확인)

- 최상위: 현행(사용 흐름, 정보 흐름, 화면 ▾, 정보 ▾) | 관리(요청 목록·상세, 리포트, 용어집). 이름은 임시
- 화면 설계서 탭은 개요·현행·히스토리만(설계·테스트·승인·메모 탭 폐지). 화면 승인 폐지, 요청 단위로 승인
- 요청 흐름: 설계 → 구현 → 테스트 → 완료. 승인은 사용자만. "설계 없음/테스트 없음" 승인 가능. 정보가 바뀌면 정보 설계, 화면이 바뀌면 클로드 디자인 시안이 설계 단계에 있어야 하고 함께 승인
- 에이전트가 발견한 것은 리포트 → 사용자가 요청으로 등록하거나 무시. 요청 번호 없는 커밋은 막는다(병합·되돌리기 제외). 요청 없는 변경은 히스토리에 "요청 없는 변경"
- 담당 에이전트 세션 하나가 요청 하나를 맡고 이름과 `claude attach <이름>`을 보여 준다. 전달은 훅(감시기 없음)
- 용어집은 우리 사정의 용어만, 에이전트가 테스트 요청 때와 주기 점검 때 관리, 화면은 용어집 페이지와 툴팁
- **사용 흐름의 기준은 화면이 아니라 사용 시나리오(유스케이스)**: 요청 범위·테스트 범위·겹침 판단도 시나리오와 컴포넌트 기준. 화면은 "보여주는 자리". 구현됨: `@does 일 | 확인 기준 | 시나리오#단계 | → 다음 단계,… | 조건` (`src/scenarios.ts`, `src/viewer/flow.ts`). 시나리오는 별도 선언 없음, 컴포넌트(`@spec`)에도 쓸 수 있음(시험 안 함)
- 확인 필요 = 기계가 판단할 수 없어 사람이 정해야 하는 것만. 코드·주석을 고치면 해소되는 것은 경고(커밋 막음)로 올려 에이전트가 해소. 확인 필요 항목은 리포트와 합쳐 "요청으로 등록 / 의도한 것"으로 처리(요청 #4와 함께, 아직 없음)
- 코드로 알 수 있는 것은 코드에서 계산하고, 사람이 적는 필드는 코드로 알 수 없는 것만
- 정보는 전체/화면용/내부용으로 계산해 구분(구현됨)
- 캔버스는 하나로 관리

- 검사: `npm run typecheck`, `node skills/spec-view/spec.mjs extract src`, `... nav --src src`, `... analyze-ts --src src --check`, `... precommit .` 모두 통과(경고 0)
